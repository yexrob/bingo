# 0016 — IM channels: one deliverer, adapters that hand over their mechanism

## Context

M13 puts a session in an IM thread: messages in, streamed replies out, approvals answered by button or keyword. The kernel side is already decided: a channel is a `Surface` (`SurfaceKind::Concurrent`) and the sdk grows no `Channel` trait (ADR-0001); `Origin{surface, principal, conversation}` carries who spoke; `Interaction` + `AnswerSpec` is the question object with a single winner; `View::text()` is the degrade; session keys follow `feishu/<chat>[/<thread>]` with first-segment ownership. The research (2026-08-31, four platforms verified) reframed the rest. Streaming is four different mechanisms: Feishu edits a *card* via CardKit (full cumulative text, QPS-exempt, 10-minute auto-close) while its plain-text edit is capped at **20 edits per message, lifetime** — works in testing, dies in production; Slack has a native token stream; Telegram and Discord only debounced edits. "Length" is characters on one platform, UTF-8 bytes on another, UTF-16 units on a third. And capability *declarations* drift — OpenClaw's Matrix adapter advertises buttons its renderer never draws — while Satori's derived capabilities cannot. The old project has no IM code to port: its `channels.rs` is the agent-room bus, re-solved in `bingo-rooms`.

## Decision

1. **One surface plugin, `bingo-channels`.** Inside it, a `ChannelAdapter` trait (crate-internal, never sdk): identity, `run` (pump inbound events), `send`, and **capabilities as accessors that hand over the mechanism** — `edit() -> Option<&dyn Edit>`, `buttons() -> Option<&dyn Buttons>`, `typing()`, `threads()`. An adapter that does not implement a mechanism cannot advertise it; the boolean cannot drift from the renderer. Beside them one `Limits` value: max text length **with its encoding** (`Chars | Utf8Bytes | Utf16Units`), markdown dialect, max actions, max label length.
2. **The `Deliverer` is a pure reducer** from session frames to delivery ops — `Open`, `Replace{full}`, `Finalize{text, question?}`, `Status`, `Resolved{by}` — laid out against a `Limits`, tested with the same frame fixtures as the TUI. Streaming is **`Replace` with the full accumulated text**, never a delta: Feishu's prefix-diff typing is unforgiving, and an adapter that prefers deltas (Slack) may diff for itself. Coalescing is a dual gate — flush on a sentence boundary, else on ≥N new chars, else on the timer — with **one pending snapshot per conversation** (a new frame replaces the queued op; the queue drains before `Finalize` so a stale snapshot can never overwrite the final text).
3. **A question is one identity down a ladder.** An open `Interaction` renders as native buttons where `buttons()` exists, else as a numbered list answered by replying `1`–`4` or the label; free text is always accepted where the spec allows it. When the kernel says resolved — by this surface or any other — the adapter **edits the delivered message: buttons stripped, outcome appended** (`approved in the TUI`), so no live button outlives its question. The kernel's single-winner rule needs nothing new.
4. **Identity and engagement.** `Origin.principal` is the platform user id, stamped by the adapter, never read from text. A P2P chat is a session; a group engages only when the bot is mentioned; a thread continues its chat's session. Keys: `<adapter>/<chat>[/<thread>]`, minted only by this plugin.
5. **One process owns one app.** Feishu's long connection is cluster-mode (a random client gets each event) and Telegram's polling mutually evicts — so a second bingo against the same credentials is a silent half-outage. The adapter takes a lock file per credential under `data_dir` and refuses loudly, never degrades quietly.
6. **The Feishu adapter** (first real one): raw `reqwest` + `tokio-tungstenite`; no SDK exists for Rust and the measured alternatives cost +51..76 crates for endpoints we do not call. The undocumented wire is accepted as a named risk with its mitigation: the **frame codec is a pure brick** — bootstrap POST, the 11-field protobuf frame hand-decoded (~150 lines, no prost), ACK-within-3s with the base64 data contract, chunk reassembly (`sum`/`seq`, 5 s), app-level ping with hot-updated intervals, a read deadline of `2×PingInterval+5 s` re-armed on every inbound frame (laptops sleep), reconnect at jitter `[0,30)` then flat 120 s, the wss URL single-use — all fixture-tested, so when the format moves one test fails and one function changes. Streaming rides **CardKit** (card entity with `streaming_mode`, full-text PUTs under one strictly-increasing `sequence`, re-armed before the 10-minute close, `streaming_mode:false` at finalize); a long transcript overflows to `post` messages (`md` + `code_block` tags); a question is its **own** card, so callbacks are never blocked by an active stream; sends queue per chat (5 QPS shared with every bot in the group); rate-limit errors drop the frame and keep streaming.
7. **The loopback adapter is the contract.** An in-crate adapter with configurable `Limits` and mechanisms, driven black-box through the real binary; every Deliverer behaviour is proven on it before Feishu exists.

## Consequences

- New deps for the Feishu adapter only: `tokio-tungstenite` (measured by the worker; budget moves by the measured number, expected ≈ +17–19). The Deliverer and loopback add none.
- Self-built (企业自建) Feishu apps only — the long connection is not offered to marketplace apps. Lark International's support is unverified; the live smoke decides it. Events during a long disconnect may be lost (at-least-once with a bounded retry ladder, no replay API): acceptable for a chat surface.
- Telegram, Slack and Discord are adapters-later: the capability matrix is recorded in the M13 plan, and the trait is proven by two implementations (loopback, Feishu) before a third exists.
- The model-facing side is untouched: whatever a surface cannot draw already folds through `View::text()` and the interaction ladder; nothing here reaches the sdk.
