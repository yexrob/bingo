## 1. openai/codex (non-TUI)

- **Kernel**: `CodexThread` owns a Submission Queue (`Op`) / Event Queue (`EventMsg`) pair. `Op::UserInput`, `ApproveExec`, `SwitchThread`, `ConfigureSession`; `EventMsg::{AgentMessage, AgentMessageContentDelta, ExecApprovalRequest, TurnStarted, TurnComplete, Error, Warning, ItemCompleted, McpToolCallEnd}`. Event `id` == originating `sub_id`. Turn = model stream → tool calls → outputs; empty output ends the Task. `TurnContext` carries per-turn env/prompt/model overrides.
- **Persistence**: `~/.codex/sessions/YYYY/MM/DD/rollout-<ts>-<uuid>.jsonl`. Each line = `RolloutLine{timestamp, ordinal?, item}`; `RolloutItem` ∈ `SessionMeta | EventMsg | ResponseItem | TurnContext | Compacted | InterAgentCommunication(+Metadata) | WorldState | RealtimeItem | SecurityRiskScore`. **New**: a `codex-state` crate mirrors metadata into *multiple* SQLite DBs (state / logs / goals / memories / queue / thread\_history); `threads` table = `id, rollout_path, created_at, updated_at, source, model_provider, cwd, title, sandbox_policy, approval_mode, archived, git_sha, git_branch, git_origin_url, memory_mode`. JSONL stays the durable replay format; SQLite is a rebuildable index. **This split is the single best idea in codex.**
- **app-server v2**: JSON-RPC 2.0 (no `"jsonrpc"` field on the wire), transports stdio/websocket/unix. Methods `thread/{start,resume,fork,list,read,revert}`, `turn/{start,steer,interrupt}`, `command/exec`, `fs/*`, `model/list`, `account/*`. Notifications `thread/started`, `turn/{started,completed}`, `turn/diff/updated`, `turn/plan/updated`, `item/{started,completed}`, `item/agentMessage/delta`. Mandatory `initialize` → `initialized` handshake; `capabilities.experimentalApi: true` opt-in; clients can opt *out* of notification methods. Schema: `codex app-server generate-ts` (ts-rs) and `generate-json-schema` (schemars), camelCase enforced.
- **execpolicy**: Starlark `.rules` files. `prefix_rule(pattern=[...,[alt1,alt2]], decision="allow"|"prompt"|"forbidden", justification=..., match=[...], not_match=[...])` — `match`/`not_match` are validated at load time, i.e. **rules carry their own tests**. `host_executable(name=, paths=[...])` pins absolute paths for basename fallback. Strictest matched severity wins. `ExecPolicyManager::create_exec_approval_requirement_for_command` → `Forbidden | NeedsApproval{proposed_execpolicy_amendment} | Skip{bypass_sandbox}`; unmatched commands fall through to `render_decision_for_unmatched_command` (dangerous-pattern heuristics × `AskForApproval` × `FileSystemSandboxKind`). Approvals can append `allow` rules at runtime.
- **apply-patch**: `*** Begin Patch` / `*** Add File:` / `*** Delete File:` / `*** Update File:` (+ `*** Move to:`, `@@` context, `*** End of File`) / `*** End Patch`. Hand-written `StreamingPatchParser` (no tree-sitter); `ParseMode::Lenient` (default, `PARSE_IN_STRICT_MODE=false`) strips heredoc wrappers. Public API: `parse_patch`, `maybe_parse_apply_patch`, `verify_apply_patch_args`, `apply_hunks`. Separately, `extract_apply_patch_from_bash` uses a **tree-sitter-bash query** anchored so `apply_patch <<EOF` (optionally `cd X && …`) must be the *only* top-level statement.
- **Tools**: `CoreToolRuntime: ToolExecutor` trait → `ToolRegistry` (`ToolName` → `RegisteredTool`) → `ToolRouter` built by `build_tool_router`, which decides model-visible tools from feature flags. `ToolOrchestrator` runs approval → select sandbox → attempt → **escalate sandbox on denial and retry**. Tools implement `Approvable` + `Sandboxable{sandbox_preference, escalate_on_failure}`. `AskForApproval ∈ {Never, OnRequest, UnlessTrusted, Granular}`. Sandbox: Seatbelt (macOS), **bubblewrap preferred over Landlock** on Linux, Windows restricted-token backend.
- **Multi-agent** (`core/src/multi_agents`, `multi_agents_v2`, `agent/registry.rs`): `CollabAgentTool ∈ {spawn_agent, send_message, followup_task, wait_agent, list_agents}`, `AgentControl::spawn_agent_with_metadata`, roles (`explorer`, `reviewer`) layered via `apply_role_to_config`, `AgentRegistry` caps sub-agent count, Guardian reviewer sub-thread for high-risk ops. Inter-agent traffic is persisted as `RolloutItem::InterAgentCommunication`.
- **Compaction**: triggered on near-exhausted context; emits `contextCompaction`; `auto_compact_fallback_prompt` tells the model to write `notes` then call `functions.new_context`, forbidding other tools; stored as `RolloutItem::Compacted{message, replacement_history?}`.
- **Plugins**: `.codex-plugin/plugin.json` — `name/version/description/author/homepage/repository/license/keywords`, component paths `skills`, `hooks` (path *or* inline), `mcpServers` (path or inline), `apps`, plus an `interface{}` block of pure UX metadata (displayName, category, brandColor, icons, screenshots). Discovery via `marketplace.json` (`plugins[]` with `name/source/policy/category`); remote install downloads a `.tar.gz` into `plugins/cache/{marketplace}/{plugin}/{version}/` and registers in `config.toml [plugins]`. Skills = folder + `SKILL.md` with YAML frontmatter (`name`, `description`), discovery `Recursive` or `DirectChildren`.
- **Login**: PKCE + loopback `http://localhost:<port>/auth/callback` (`mcp_oauth_callback_port`), tokens in `auth.json`, storage mode `Keyring|File|Auto`, auto-refresh via `AuthManager`, `CODEX_API_KEY` fallback.
- **MCP**: qualified names `mcp__{server}__{tool}`; `codex-mcp-server` exposes the same thread/turn RPCs over stdio.

**Verdict** — (a) nothing. (b) Op/Event split; thread/turn/item; JSONL+SQLite index; execpolicy decision lattice; plugin manifest. (c) port `execpolicy` (Starlark via `starlark` 0.14 + `shlex`), `apply-patch`, the bash-AST safe-command extractor, seatbelt/landlock/bwrap wrappers. (d) don't replicate the crate explosion or v1/v2 + multi\_agents/multi\_agents\_v2 duplication.

https://github.com/openai/codex/tree/main/codex-rs · https://deepwiki.com/openai/codex

## 2. aaif-goose/goose

- **GDK crates are real** (deepwiki's index is stale and denies they exist — trust crates.io). All at `0.1.0-alpha.7`, 2026-08-27, Apache-2.0, edition 2021, MSRV 1.94.1: `goose-sdk` (114 dl), `goose-agent` (87 dl total, **15 downloads on the latest version**, 934 LoC / 5 files), `goose-sdk-types`, `goose-provider-types`, `goose-providers`, `goose-context-management` ("Conversation compaction for Goose"), `goose-local-inference`, `goose-download-manager`.
- **`goose-agent` public API** (docs.rs, 3.03% documented): modules `machine` (`StateMachine`, `Step`, traits `EffectHandler`, `EffectUsage`, `MachineSession`, `SessionLoader`), `events` (`AgentEvent`), `operation` (`Operation` trait, `MachineEffect`, `Inference`, `Emitter`, `InferenceInput`, `SlashCommand`, `StepResult`, `ConversationEffect`, `OperationResult`, `OperationFuture`, helpers `applied/yielded/yielded_with/not_applicable/ends_turn/assistant_turn_count/messages_since_kickoff/last_effective_role/trailing_error`), `inference` ("provider inference operation for the unrolled agent loop"). So: **the loop is an effect-driven state machine, and it *is* designed as a reusable library** — but it's 934 lines, 15 downloads, undocumented, and alpha.
- **`goose-sdk` deps** (verified): `agent-client-protocol ^2.0.0`, `agent-client-protocol-schema =1.5.0` (**pinned two minors behind the published 1.7.0**), `goose-sdk-types`, optional `rmcp ^3.0 (schemars, auth)`, `goose-providers (rustls-tls)`, `goose-context-management`, `uniffi ^0.32`. No reqwest/sqlite/axum → the SDK is deliberately thin.
- **Extensions** = `ExtensionConfig ∈ {Builtin, Platform, Stdio, StreamableHttp, Frontend, InlinePython, Sse(unsupported)}`; `Extension` trait = `name/description/instructions/tools/status/call_tool`; managed by `ExtensionManager`. Everything is MCP under the hood.
- **Permissions**: `GOOSE_MODE ∈ {auto, approve, smart_approve, chat}` × per-tool `PermissionLevel ∈ {AlwaysAllow, AskBefore, NeverAllow}`, persisted by `PermissionManager`. Dispatch through `ToolInspectionManager` running a chain of `ToolInspector`s → `InspectionAction{Allow, Deny, RequireApproval}`: `PermissionInspector`, `SecurityInspector` (prompt-injection), `EgressInspector`, `AdversaryInspector` (LLM review, enabled by `~/.config/goose/adversary.md`), `RepetitionInspector` (loop breaker). **The inspector-chain shape is the best-designed permission layer of the nine references.**
- **Sessions**: migrated (v1.10.0) from `~/.local/share/goose/sessions/*.jsonl` to **SQLite `sessions.db`** in the same dir (`%APPDATA%\Block\goose\data\sessions\` on Windows); old JSONL auto-imported then abandoned. Session IDs `YYYYMMDD_<N>`. Stores metadata, messages, tool calls/results, token usage, extension config.
- **Recipes**: YAML/JSON `title/description/instructions/prompt/extensions/parameters/sub_recipes/settings/retry/activities`; `RecipeParameter{requirement: Required|Optional|UserPrompt, input_type: String|Number|Boolean|Date|File|Select}`; `{{var}}` templating. Each `sub_recipes[]` entry becomes a generated tool that runs in an **isolated session with no shared history**; nesting prohibited; ≤10 concurrent workers. Subagents = ad-hoc prompt-defined, no extension management.
- **ACP**: no `goose-acp` crate — it's `crates/goose/src/acp/server.rs`, `goose acp` serves stdio JSON-RPC for Zed/JetBrains. Goose is also an ACP **client**: `AcpProvider` / `ClaudeAcpProvider` drives Claude Code or Codex as a provider, forwarding its own extensions as MCP servers to them.
- **Compaction**: auto at 80% of the token limit (`GOOSE_AUTO_COMPACT_THRESHOLD`), prompt template in `compaction.md`, plus background summarization of older tool outputs while recent ones stay full-fidelity.

**Is depending on `goose-agent` alpha viable?** — **No, it's a trap.** 15 downloads on latest, 3% doc coverage, alpha.7 with no stability promise, a pinned `=1.5.0` schema dep that will conflict with your own ACP stack, and it drags `goose-provider-types`/`goose-providers` into your provider layer. Do the opposite: **depend on `goose-context-management` alone** (small, single-purpose, replaceable) if it fits, and copy the effect-machine shape.

**Verdict** — (a) at most `goose-context-management`. (b) inspector chain; ACP-both-directions; recipes/sub-recipes. (c) `PermissionInspector` semantics; sub-recipe→tool generation. (d) `goose-agent` as a dependency; SQLite-only sessions; InlinePython extensions.

https://github.com/aaif-goose/goose · https://crates.io/crates/goose-agent · https://docs.rs/goose-agent

## 3. pi (badlogic/pi-mono → `earendil-works/pi`)

- **pi-ai stream events (exactly 12)**: `start`, `text_start`, `text_delta`, `text_end`, `thinking_start`, `thinking_delta`, `thinking_end`, `toolcall_start`, `toolcall_delta`, `toolcall_end`, `done{reason, message}`, `error{reason, error}`. Every block event carries `contentIndex`. Messages: `UserMessage | AssistantMessage{content, api, provider, usage, stopReason} | ToolResultMessage{toolCallId, toolName, isError}`; content blocks `text | image{data, mimeType} | toolCall{name, arguments} | thinking`.
- **Quirk handling**: a per-model `compat` record (supports-usage-in-streaming, maxTokens field name, requires-tool-result-names…) plus `thinkingLevelMap` mapping `minimal|low|medium|high|xhigh|max` → provider value or `null`. Cross-provider handoff transforms thinking blocks into `<thinking>` text. `Api` = wire protocol (`anthropic-messages`, `openai-responses`, `openai-completions`, `google-generative-ai`); `Provider` = runtime unit (id, auth methods, model listing, stream behaviour) built by `createProvider()`; `Models` registry auto-generated, `getModel()` sync + `refresh()` async.
- **pi-agent-core**: `agentLoop(prompts, context, config, signal, streamFn)` and `agentLoopContinue(context, …)` (throws if last message is `assistant`), wrapped by a stateful `Agent`. Two queues via `PendingMessageQueue` (`one-at-a-time` | `all`): **steering** (injected after a turn completes, can interrupt while tools run) and **follow-up** (drained only when no tool calls and no steering pending). `toolExecution: "parallel" | "sequential"` — parallel preflights sequentially, runs concurrently, but **persists `toolResult`s in original assistant order**. Hooks `beforeToolCall` (→ `{block:true}`) / `afterToolCall` (mutate result, `terminate` flag). Events: `agent_start/end`, `turn_start/end`, `message_start/update/end`, `tool_execution_start/update/end`. Context management is a callback pair: `transformContext(AgentMessage[])` then required `convertToLlm()`.
- **pi-coding-agent extensions**: default-exported TS factory receiving `ExtensionAPI`; loaded via `jiti` (no build step) from `~/.pi/agent/extensions/*.ts`, `.pi/extensions/*.ts` (project-local only **after trust**), `settings.json` paths, `pi -e ./x.ts`, or npm/git "pi packages" with their own `package.json`. Surface: `registerTool` (typebox schemas), `registerCommand`, `registerShortcut`, `registerFlag`, `on(event, handler)`, `appendEntry` (persist custom state into the session), `ctx.ui.{confirm,select,input,notify,setStatus,setWidget,custom}`.
- **Hook points** (~35): `project_trust`, `session_start`, `resources_discover`, `input`, `before_agent_start`, `agent_start`, `message_start/update/end`, `turn_start/end`, `context`, `before_provider_headers`, `before_provider_request`, `after_provider_response`, `tool_execution_start`, `tool_call`, `tool_execution_update`, `tool_result`, `tool_execution_end`, `agent_end`, `agent_settled`, `session_before_switch`, `session_shutdown`, `session_before_fork`, `session_info_changed`, `session_before_compact`, `session_compact`, `session_before_tree`, `session_tree`, `model_select`, `thinking_level_select`.
- **Session tree JSONL** — `log.jsonl`, every entry `SessionEntryBase{id, parentId (null at root), timestamp}` forming a DAG, with `leafId` as the cursor. `type ∈ session | message | compaction | branch_summary | model_change | thinking_level_change | custom | custom_message | label | session_info`. `/tree` navigates, `/fork` writes a new file from a chosen user message, `/clone` duplicates the active branch, `pi -c` / `-r` / `--session` / `--fork` from the CLI. Format v3 renamed `hookMessage` → `custom`.
- **Compaction**: auto when estimated tokens > context window − `reserveTokens` (16384 default), keeping `keepRecentTokens` (20000 default); `/compact [instructions]` manual; `SUMMARIZATION_SYSTEM_PROMPT`, prior summary fed back for iterative refinement; stored as `CompactionEntry{summary, firstKeptEntryId, tokensBefore, details?, usage?, retainedTail?}` — `retainedTail` makes it a **self-contained checkpoint**.
- **Headless**: `--mode json` (all session events as JSON lines), `--mode rpc` (stdin/stdout process integration), `-p/--print`, `--no-session`, `--session-dir`, `--approve/--no-approve`.

**Verdict** — (b) copy: the 12 stream events, steering/follow-up split, session-tree JSONL, unified extension API, compaction entry format. (c) port: the provider-quirk table, `SessionManager`, `agentLoop`/`agentLoopContinue` split, compaction utilities. (d) don't try to reproduce `AgentMessage` declaration-merging in Rust — model it as `enum Entry { … , Custom { kind: String, data: serde_json::Value } }`.

## 4. opencode (anomalyco/opencode, 202k★)

- **Server/client**: headless HTTP server (`opencode serve`) with an OpenAPI 3.1 spec; the TUI is just one client. Built on `@effect/platform`; middleware stack = error handling, compression, CORS, authorization, workspace isolation.
- **Event bus**: single SSE endpoint `GET /global/event`; an `EventV2Bridge` pipes internal bus events out. Events: `EventSessionCreated/Updated/Deleted`, deltas `EventSessionNextTextDelta`, `…NextReasoningDelta`, `…NextToolInputDelta`, `…NextToolOutputDelta`, `…NextToolErrorDelta`, `…NextToolCallDelta`, interactive `EventPermissionV2Asked` / `EventQuestionV2Asked`, plus `EventSessionTodo*`, `EventSessionFileDiff`, `EventSessionFileTree`, `EventSessionShell`.
- **Endpoints**: `GET/POST /session`, `GET /session/:id`, `POST /session/:id/message` (sync), `POST /session/:id/prompt_async`, `/config`, `/provider`, `/agent`, `/file/content?path=`, `/global/health`.
- **Data model**: Session → Message → `Part`, where `Part` = `TextPart | ReasoningPart | ToolPart | FilePart | StepStartPart | StepFinishPart | SnapshotPart | PatchPart | AgentPart | SubtaskPart | RetryPart | CompactionPart`. **This is the most complete "part" taxonomy in the survey** — note `SnapshotPart`, `PatchPart`, `RetryPart`, `CompactionPart` as first-class parts.
- **Storage**: hybrid. SQLite (`Global.Path.data/opencode.db`, Drizzle ORM) holds `SessionTable` / `MessageTable` / `PartTable` / `ProjectTable`; a file `Storage.Service` holds bulkier JSON (`session_diff/<id>.json`, summaries) under `~/.local/share/opencode/project/<slug>/storage/` (or `project/global/storage/` for non-git dirs). Pre-migration layout was `session/<projectID>/<sessionID>.json`, `message/<sessionID>/<messageID>.json`, `part/<messageID>/<partID>.json`. Permissions live **inside** `SessionTable.permission` as a JSON `PermissionV1.Ruleset`.
- **Plugins**: `Plugin = (input: PluginInput, opts?) => Promise<Hooks>`; `PluginInput{client (SDK), project, directory, worktree, $ (Bun shell)}`. Hooks: `event`, `chat.message`, `chat.params`, `permission.ask` (→ `ask|deny|allow`), `tool.execute.before`, `tool.execute.after`, `auth` (dynamic credentials/methods), `provider` (inject model lists). Loading: `.opencode/plugins/*.{ts,js}` (project), `~/.config/opencode/plugins/` (global), plus npm packages listed in `opencode.json`'s `plugin[]`, auto-installed with Bun. Custom tools via the `tool()` helper (Zod args) — **plugin tools shadow built-ins of the same name**.
- **Agents/commands**: markdown with frontmatter in `.opencode/agent/*.md` (`description`, `mode: primary|subagent|all`, `model`, `permission`, body = prompt) or inline in `opencode.json`. Built-ins: `build`, `plan` (primary); `general`, `explore` (read-only), `scout` (subagents). Commands in `.opencode/command/*.md` with `$ARGUMENTS` / `$1`. Per-agent permission list: `bash, read, edit, glob, grep, webfetch, task, todowrite, websearch, lsp, skill`.

**Verdict** — (b) copy the SSE-bus-as-sole-contract, the `Part` union, agent-as-markdown with `mode`, and per-session permission rulesets. (c) port the `permission.ask`/`tool.execute.*` hook shapes. (d) avoid the two-store split (SQLite + JSON files) — use codex's JSONL-primary + SQLite-index instead.

## 5. Anthropic Claude Agent SDK & `stream-json`

- **CLI surface** (verified from docs): `claude -p "…" --output-format text|json|stream-json [--verbose --include-partial-messages] [--input-format stream-json] --allowedTools "Bash(git diff *),Read" --permission-mode auto|dontAsk|acceptEdits --json-schema '<JSONSchema>' --resume <id> --continue --fork-session --bare --add-dir --mcp-config --agents --plugin-dir --plugin-url --append-system-prompt[-file] --forward-subagent-text`.
- **stream-json output**: NDJSON, each line has `type` (+ usually `subtype`). First line is `system`/`init` carrying `model`, `tools`, `mcp_servers[{name,status}]`, `mcp_server_errors[{name,type,message}]`, `plugins[{name,path}]`, `plugin_errors[{plugin,type,message}]`, `capabilities[]` (e.g. `interrupt_receipt_v1`), `session_id`, `uuid` — preceded only by `system/plugin_install` and `hook_started|hook_progress|hook_response` events. Other system subtypes: `api_retry{attempt, max_retries, retry_delay_ms, error_status, error, uuid, session_id}`. `assistant`/`user` messages carry **`parent_tool_use_id`** (null = main thread, else the spawning tool-call id — this is how you reconstruct the sub-agent tree at any depth). `SDKPartialAssistantMessage` = `{type:"stream_event", event: BetaRawMessageStreamEvent, parent_tool_use_id: null, uuid, session_id, ttft_ms?}` — i.e. the **raw Anthropic API event passed through**. Last line is `result` with `result`, `session_id`, `total_cost_usd` + per-model breakdown, `structured_output`, `subtype: success|error_max_turns|…`. A `compact_boundary` message marks compaction (TS `SDKCompactBoundaryMessage`; Python `SystemMessage` subtype `compact_boundary`).
- **Hooks** (~30 events, config in `~/.claude/settings.json`, `.claude/settings.json[.local]`, managed policy, plugin `hooks/hooks.json`, or skill/subagent frontmatter): `SessionStart` (matchers `startup|resume|clear|compact|fork`), `Setup`, `UserPromptSubmit`, `UserPromptExpansion`, `PreToolUse`, `PermissionRequest`, `PermissionDenied`, `PostToolUse`, `PostToolUseFailure`, `PostToolBatch`, `Stop`, `StopFailure`, `SubagentStart`, `SubagentStop`, `TaskCreated`, `TaskCompleted`, `TeammateIdle`, `Notification`, `MessageDisplay`, `InstructionsLoaded`, `ConfigChange`, `CwdChanged`, `DirectoryAdded`, `FileChanged`, `PreCompact`, `PostCompact`, `Elicitation`, `ElicitationResult`, `WorktreeCreate`, `WorktreeRemove`, `SessionEnd`. Common input: `session_id, prompt_id, transcript_path, cwd, permission_mode, hook_event_name, agent_id, agent_type`; tool events add `tool_name, tool_input, tool_use_id`. Output: `{hookSpecificOutput:{hookEventName, permissionDecision:"allow"|"deny", permissionDecisionReason, additionalContext, updatedInput}, systemMessage, terminalSequence}`. **Exit 2 = blocking**, stderr becomes the reason. Handler types: `command`, `http`, `mcp_tool`, `prompt`, `agent` — note the last two are *LLM-backed hooks*. Matchers are exact-or-regex with an `if: "Bash(rm *)"` guard.
- **Permissions**: `canUseTool` fires only when the flow falls through to a prompt (not for auto-approved calls), and is shadowed by `allowedTools`/`bypassPermissions`. Rule syntax `Bash(git diff *)` — the space before `*` matters.
- **Plugins**: `.claude-plugin/plugin.json` with component paths `skills`, `commands`, `agents`, `hooks`, `mcpServers`, `lspServers`, `outputStyles`, `experimental.themes`, `experimental.monitors`; `userConfig{}` (types `string|number|boolean|directory|file`, `sensitive`, exposed as `${user_config.KEY}` and `CLAUDE_PLUGIN_OPTION_<KEY>`); `dependencies[]` with semver. Layout `skills/<n>/SKILL.md`, `commands/*.md`, `agents/*.md`, `hooks/hooks.json`, `.mcp.json`, `.lsp.json`, `bin/` (added to Bash PATH). Vars `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}`, `${CLAUDE_PROJECT_DIR}`. Scopes `user|project|local|managed`.
- **Who consumes stream-json**: OpenClaw's `claude-cli` backend (`jsonlDialect: "claude-stream-json"`, keeps a persistent stdio process, sends follow-ups over stream-json stdin, requires a `msg_lifecycle_v1` capability); Hermes imports `~/.claude/projects/<encoded-cwd>/<uuid>.jsonl` transcripts; plus an ecosystem of parsers (`claude-code-parser`) and wrapper harnesses.

**Should bingo's `--output-format stream-json` be wire-compatible?** — **Yes, at the envelope level; no, internally.** Emit the same NDJSON envelope (`system`/`init`, `assistant`, `user`, `result`, `stream_event`) and — critically — the same `parent_tool_use_id` and `session_id` fields, because that is exactly what OpenClaw's `claude-stream-json` dialect and every third-party supervisor parse. Do **not** adopt `stream_event.event` = raw Anthropic `BetaRawMessageStreamEvent` as your kernel's event type; keep the AI-SDK-V3-shaped internal enum and render the Anthropic shape only in the compatibility encoder. That gives you a `claude-stream-json`-dialect backend in OpenClaw with zero plugin work on day one.

## 6. `@ai-sdk/provider` vs litellm

**Verified `LanguageModelV3StreamPart` (19 kinds, from `packages/provider/src/language-model/v3/language-model-v3-stream-part.ts` on `main`):**

`text-start{id, providerMetadata?}` · `text-delta{id, delta, providerMetadata?}` · `text-end{id}` · `reasoning-start{id}` · `reasoning-delta{id, delta}` · `reasoning-end{id}` · `tool-input-start{id, toolName, providerExecuted?, dynamic?, title?}` · `tool-input-delta{id, delta}` · `tool-input-end{id}` · **`tool-approval-request`** · `tool-call` · `tool-result` · `file` · `source` · `stream-start{warnings}` · `response-metadata` · `finish{usage, finishReason, providerMetadata?}` · `raw{rawValue}` · `error{error}`.

Prompt: `LanguageModelV3Prompt = Message[]` where `system` → string, `user` → `(Text|File)[]`, `assistant` → `(Text|File|Reasoning|ToolCall|ToolResult)[]`, `tool` → `ToolResult[]`; every message may carry `providerOptions`. V2→V3 changes: `promptTokens/completionTokens` → `inputTokens/outputTokens` with `totalTokens` required; `rawResponse` → `response`; start/delta/end + IDs everywhere.

**litellm** normalizes to the OpenAI `chat.completion.chunk` shape (`choices[].delta.{role,content,tool_calls}`, `finish_reason`). That is lossy for exactly what a coding agent needs: no block IDs, reasoning bolted on as `reasoning_content`, tool arguments only as index-keyed partials, no approval or file/source parts.

**Verdict: model bingo's kernel stream on `LanguageModelV3StreamPart`, not litellm.** It is the only unified model with (i) stable per-block IDs, (ii) first-class `tool-input-*` streaming distinct from `tool-call`, (iii) a `tool-approval-request` part that maps directly onto your permission engine, and (iv) `raw` as an explicit escape hatch. Cross-check against pi-ai's 12 events (same skeleton, `contentIndex` instead of `id`) — where they disagree, prefer AI-SDK's `id` (survives interleaved/parallel blocks; `contentIndex` doesn't).

## 8. crush and aider — one mechanism each

**crush** (Go, 27.8k★, active): the mechanism worth stealing is *diagnostics-as-context*. An `lsp.Manager` owns the server lifecycle (user-configured or `auto-lsp`); when an LSP is live the coordinator's `buildTools` injects `NewDiagnosticsTool`, `NewReferencesTool`, `NewRenameTool` into the tool set, and — the key detail — `openInLSPs` opens a file into the servers and `waitForLSPDiagnostics` **blocks until diagnostics are published** before a read-only tool returns, so the model sees the compiler's opinion of the file it just edited within the same turn rather than a stale one. UI state is memoized with an `lspStatesTTL` re-probe backstop for missed events. Secondary steal: `permissions allow` / `permissions deny` as *separate* lists where deny removes the tool from the model's context entirely rather than failing at call time, plus `--yolo`. Sessions/messages in SQLite with real migrations. (Providers come from Catwalk, a remote model DB — don't copy that coupling.)

**aider** (Python, 48.6k★, **dormant since 2026-05-22**): steal `repomap.py` wholesale. Symbols are extracted with tree-sitter through `grep_ast` using per-language `.scm` tag queries into `Tag{rel_fname, fname, line, name, kind}`; a `networkx.MultiDiGraph` is built with files as nodes and def→ref edges weighted by reference count, `personalization` boosted for files in the chat and identifiers mentioned in the current message; `networkx.pagerank` ranks them; ranks are pushed down to individual definitions; then `get_ranked_tags_map_uncached` **binary-searches the number of definitions that fits `max_map_tokens`** and renders them with `grep_ast.TreeContext` as an elided source tree. Two-level cache: SQLite tags cache at `.aider.tags.cache.v{N}` (falls back to an in-memory dict) plus a map cache keyed by (chat files, other files, max tokens, mentioned files, mentioned idents). This is the best-documented answer to "what do I put in the system prompt about a repo I haven't read", and it ports cleanly to Rust (`petgraph` has PageRank-able primitives; you already need tree-sitter). Edit formats: `whole` / `diff` (search-replace "editblock", the default and most reliable) / `udiff` / `architect`.

## 9. Zed + ACP

- **Depend on the crates.** `agent-client-protocol` 2.0.0 (Apache-2.0, **1.85M recent downloads**, updated 2026-07-23), `agent-client-protocol-schema` 1.7.0 (2.04M, 2026-08-20), `agent-client-protocol-tokio` 0.11.1, `agent-client-protocol-rmcp` 3.0.0. Zed stashes the tool's programmatic name in the ACP `ToolCall` `meta` under a `TOOL_NAME_META_KEY` — a hint that ACP's `ToolCall` is under-specified and you will need `meta` too.

## The five answers

### (i) Is there a published Rust crate with a Claude-Code-style permission rule engine, or a reusable coding-agent loop?

**No — nothing you should depend on.** I searched crates.io across "coding agent loop", "agent permission policy tool approval", "llm provider streaming unified", "agent-client-protocol", "claude-rust" and "goose".

- **Permission engines**: `destructive_command_guard` 0.13.0 (Dicklesworthstone, 189 recent dl, ~190k LoC, **license changed from MIT to non-standard after 0.5.6**) is a hook that blocks destructive commands — usable as a *hook binary*, not as a rule engine library. `claude-rust-permission` 2.0.2 (164 dl, single author, untouched since 2026-04-11) does implement `bash(git *)` / `deny: bash(rm -rf *)` style rules but the whole `claude-rust-*` workspace (17 crates, 7–600 downloads each) is a hobby reimplementation and is stale. `brainwires-permission`, `rullama-permission`, `tirea-extension-permission` are framework-internal splits with <300 downloads.
- **Agent loops**: `goose-agent` 0.1.0-alpha.7 (87 dl) is the only one from a serious project — and see §2 for why not. Everything else (`agent-code-lib`, `oxi-agent` 0.64.0, `oxicode-agent`, `stynx-code-engine`, `capo-agent`, `opi-agent`, `agentix`, `io-harness`, `oneharness`, `baseplate`, `symbiont`, `pi_agent_rust`) is single-vendor, rapid-major-version churn, low downloads — the classic signature of published-by-an-agent crates. `pi_agent_rust` 0.3.0 (2,886 recent dl) is an unofficial Rust port of Pi Agent, not affiliated with `earendil-works/pi`.
- **The genuinely dependable crates in this space** are the protocol/transport layer only: `agent-client-protocol` 2.0.0, `agent-client-protocol-schema` 1.7.0, `agent-client-protocol-tokio` 0.11.1, `rmcp` 3.1.4 (11.5M recent dl, features `server`, `macros`, `transport-child-process`, `transport-streamable-http-{client,server}`, `auth`, `schemars`, `elicitation`, `tower`), `async-openai` 0.41.3, plus `starlark` 0.14 + `shlex` + `tree-sitter-bash` if you port execpolicy.

**Conclusion: write bingo's permission engine and loop yourself.** The permission engine is genuinely a place where "adopt" isn't on the table, and it's the highest-value thing you'd own.

### (ii) Best plugin/extension API to model on

**pi-coding-agent, with three grafts.**

It wins because it is the only one where tools, slash commands, keyboard shortcuts, CLI flags, UI surfaces, lifecycle hooks and persistent session state are **one API object** (`ExtensionAPI`) registered by one factory function — which is exactly bingo's "everything-as-plugin" thesis. Its ~35 hook points are also the finest-grained set available, and uniquely include provider-level interception (`before_provider_headers`, `before_provider_request`, `after_provider_response`) and `agent_settled` (distinct from `agent_end` — fires only after retries *and* compaction finish; you will want this for IM gateways deciding when to post).

Graft on:
1. **Claude Code's declarative manifest** (`plugin.json` component paths + `userConfig` typed options + `${PLUGIN_ROOT}`/`${PLUGIN_DATA}` + `dependencies`) — pi has no manifest, and you need one for a marketplace and for loading plugins without executing code first. Codex's `.codex-plugin/plugin.json` is the same design with an added `interface{}` presentation block; take that too.
2. **OpenClaw's `activation{onStartup, onCommands, onChannels, onCapabilities, …}`** — lazy activation matters once you have hundreds of plugins, and it's the only reference that solves it.
3. **opencode's `permission.ask` hook** returning `allow|deny|ask` — cleaner than pi's boolean `beforeToolCall` block.

Rust-specific: pi's model relies on `jiti` running TS with no build step. Your equivalent tiers should be (a) native Rust plugins as in-process trait objects for built-ins, (b) MCP stdio/HTTP servers for tools (rmcp gives you both sides), (c) declarative markdown/TOML for agents, commands, skills and hooks, (d) a scripting escape hatch for the long tail. Do **not** make WASM the primary mechanism — none of the nine references did, and Codex's `codex-v8-poc` suggests even OpenAI is still experimenting.

Reject: goose (extensions ≡ MCP servers only — no commands/UI/hooks, too narrow); OpenClaw plugin-sdk (correct as a *consumer* contract for you to satisfy, but its surface is gateway/channel-shaped, not agent-shaped); opencode (right hooks, wrong host — Bun `$` and Effect are not portable).

### (iii) Best session persistence format

**Codex's model — append-only JSONL as the source of truth + a rebuildable SQLite index — with pi's tree semantics inside the JSONL.**

Reasoning by elimination: goose threw away JSONL for SQLite and now has no replayable event log (its own docs say old `.jsonl` files are imported "but no longer actively managed") — that's a one-way door. opencode runs SQLite *and* JSON files, i.e. two sources of truth, violating 守一. Claude Code's flat JSONL transcript is replayable but has no branching, so `--fork-session` has to copy files.

Concretely for bingo:
- One `log.jsonl` per session. Every line: `{id, parentId, timestamp, type, …}` — pi's DAG, which gives you `/fork`, `/tree`, `/clone` and revert **for free and in-place**, versus codex's `thread/fork` which spawns a new rollout file.
- Entry `type` set merged from pi and codex: `session` (header: version, id, cwd, parentSession), `message`, `turn_context`, `compaction`, `branch_summary`, `model_change`, `custom` (extension state, not in LLM context), `custom_message` (extension state, in LLM context), `label`, `session_info`, `inter_agent` (codex's `InterAgentCommunication` — you need this for teams), and `part`-level entries following opencode's union where a tool call needs `SnapshotPart`/`PatchPart` semantics.
- A SQLite DB alongside, holding **only derived data**: `threads(id, log_path, created_at, updated_at, cwd, title, git_sha, git_branch, git_origin_url, model_provider, approval_mode, archived, …)` plus FTS over messages. Rule: **deleting the DB must lose nothing.** That single invariant is what makes this design correct and goose's incorrect.
- Path layout: codex's `sessions/YYYY/MM/DD/` beats a flat directory for scanning, and beats opencode's per-project-slug directories for cross-project resume (Claude Code just fixed a bug where it couldn't find sessions outside the current project — don't reintroduce it).

### (iv) Best multi-agent design

**Codex's collab tool-set + registry, with goose's isolation rule and Claude Code's `parent_tool_use_id` wire convention.**

- **Tools, not a magic `task` tool.** Codex's `CollabAgentTool` decomposes delegation into five verbs — `spawn_agent`, `send_message` (queue without triggering a turn), `followup_task` (message + trigger turn), `wait_agent` (block until sub-agents reach a terminal state), `list_agents`. This is strictly more expressive than Claude Code's / opencode's single fire-and-forget Task/`task` tool, and it is the only design in the survey that supports *actual collaboration* (a parent nudging a running child) rather than fan-out/fan-in. For "team collaboration first-class", this is the model.
- **Roles as config layers**: codex's `apply_role_to_config` layers a role (`explorer`, `reviewer`) over the parent's config — combine with opencode's `mode: primary|subagent|all` markdown-frontmatter agent files, which is the nicest *authoring* surface (frontmatter for description/model/tools/permission, body = system prompt).
- **Isolation**: goose's rule — sub-agents share no conversation history, memory or state, nesting of sub-recipes is forbidden, and concurrency is capped (10). Codex enforces the cap in `AgentRegistry`. Claude Code caps subagent depth at 1 by default and concurrency at 20. Take: **hard depth and breadth caps in the kernel, isolated context by default, explicit message-passing as the only channel.**
- **Observability**: persist inter-agent traffic as first-class log entries (codex's `InterAgentCommunication`), and on the wire tag every sub-agent message with `parent_tool_use_id` (Claude Code) so any host can reconstruct the tree at arbitrary depth. Add codex's Guardian pattern — a reviewer sub-agent gating high-risk operations — as a *plugin*, not a kernel feature.

### (v) Best compaction design

**pi's `CompactionEntry` as the storage format; goose's two-tier policy as the trigger.**

- **Format** (pi, and it's not close): compaction is an *entry in the session log*, not a rewrite of it — `{type:"compaction", summary, firstKeptEntryId, tokensBefore, usage?, details?, retainedTail?}`. Because it names a cut point by entry id rather than replacing history, the raw history stays fully intact and inspectable, `/tree` can navigate *across* a compaction, and a prior summary can be fed back for iterative refinement on the next compaction. `retainedTail` makes the entry a self-contained checkpoint you can load without walking the log. Codex's `Compacted{message, replacement_history}` is the same idea but replacement-shaped (lossier); Claude Code emits only a `compact_boundary` marker; opencode has a `CompactionPart`; goose stores nothing structured.
- **Trigger** (goose): auto-compact at a configurable fraction of the context limit (80% default, env-overridable), **plus** a second tier — background summarization of *older tool outputs* while recent ones stay full-fidelity, with the cutoff derived from the limit and the threshold. Tool output is where a coding agent's context actually goes; summarizing it separately from the conversation is the single highest-leverage trick in the survey. pi's numbers are a good default shape: compact when `estimated > window - reserveTokens(16384)`, keep `keepRecentTokens(20000)`.
- **Prompt as data**: goose's `compaction.md` and pi's `SUMMARIZATION_SYSTEM_PROMPT` are both user-editable templates — make it a plugin-overridable resource, with hooks around it (pi's `session_before_compact`/`session_compact`, Claude Code's `PreCompact`/`PostCompact`).
- **Avoid** codex's `auto_compact_fallback_prompt` approach (tell the model to save `notes` then call `functions.new_context`, forbidding other tools). It puts a hard-failure path in the model's hands at exactly the moment the context is exhausted. Compaction should be a kernel operation the model cannot decline.
- Publish `contextCompaction` / `compact_boundary` on the event stream in both directions — an IM gateway needs to know a summary happened, and `agent_settled` (pi) rather than `agent_end` is the right "safe to post" signal because it fires after compaction and retries.
